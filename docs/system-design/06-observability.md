# 06. Observability

## Goal

Observability in this project should be lightweight but intentional.

The current repository already has a few useful visibility mechanisms, but it does not yet implement the full request-correlation strategy originally proposed in the design notes.

This document therefore separates:

- what is implemented now
- what is planned next for a stronger MVP tracing story

## Current implementation

### API inspection and health

The backend currently exposes:

- Swagger at `/docs`
- a health endpoint at `/api/health`

These provide quick local visibility into:

- whether the API is up
- what endpoints exist
- what DTO shapes the API expects

### Response normalization

The backend currently includes:

- a global success-response interceptor
- a global exception filter

This means frontend and manual API consumers already receive predictable envelopes for:

- successful responses
- validation errors
- auth failures
- unhandled application errors

### Validation visibility

The global `ValidationPipe` already makes payload issues visible by:

- rejecting unknown fields
- transforming query values
- surfacing validation failures consistently

This is not a full observability system, but it does improve runtime clarity.

### Runtime logging today

At the moment, runtime logging mostly relies on the default Nest startup and runtime output.

That is acceptable for early local development, but it is still limited because there is no:

- structured request logger
- request duration logging
- request ID correlation
- Prisma-to-request trace linkage

## Current gaps

The following design goals are still not implemented in source:

- request correlation through a request ID
- structured backend logs for every request
- timing visibility for request lifecycle and database access
- lightweight tracing across `web -> api -> db`

These remain valid targets, but the docs should not present them as already complete.

## Planned next increment

The next observability increment should answer four practical questions:

- what request failed
- where it failed
- how long it took
- which database work was triggered by that request

## Recommended MVP observability target

| Concern | Recommended next step |
| --- | --- |
| Startup status | keep Nest startup logs and health endpoint |
| API inspection | keep Swagger as the local inspection surface |
| Request correlation | add a request ID generated by API or propagated from web |
| Backend logging | add structured logs with route, method, status, and duration |
| Error visibility | log normalized error context before returning API error envelopes |
| Request-path tracing | correlate web request, API handling, and Prisma operations by request ID |
| Timing visibility | log request duration and key persistence operation timing |

## Request ID strategy

The intended lightweight tracing model is still correlation-based rather than full distributed tracing.

Recommended approach:

- the web application may send a request ID header
- if the client does not send one, the API should generate one
- the API should return the final request ID in the response headers
- the same request ID should appear in request logs and Prisma-related logs

This would allow a single action to be followed across:

`browser action -> API route -> service logic -> Prisma operation`

## Logger strategy

The backend does not need a heavy observability vendor for this challenge.

A practical logger should capture:

- timestamp
- level
- request ID
- method
- route
- response status
- duration
- error message when relevant

That would be enough to meaningfully debug most MVP issues.

## Prisma visibility strategy

For this project, Prisma-level tracing should stay lightweight.

Recommended approach:

- log model and operation type for important writes
- capture duration for slow or important queries
- attach request ID context from the parent API request when possible

Full SQL tracing is unnecessary for the interview scope.

## Suggested implementation direction

This can be implemented proportionally through:

- a NestJS middleware or interceptor for request ID propagation
- a centralized logger service
- request lifecycle timing around controller execution
- Prisma query-event or service-level logging with correlation context
- frontend request helpers that optionally attach a request ID header

## Design principle

The observability strategy should stay proportional to the size of the system:

- simple enough for an interview project
- clear enough to show engineering maturity
- practical enough to support real debugging of the MVP
